# Workstation and publication contract

## Commands and authority

The planned Git-pinned launcher is `specs/015-learned-program-search/validation/launch-round028.sh REV ACTION`. It executes the candidate's standard-library host CLI as `python3 scripts/foundation_run.py --engine podman discovery round028 --action ACTION --workspace ROOT` from verified candidate source. The engine remains an explicit foundation option. Supply the absolute physical donor workspace as ROOT. All actions refer to the same session, `run-state/discovery/015-research-round-028`. The [quickstart](../quickstart.md) distinguishes currently available Git commands from the planned interface.

The archive-only CLI form is `python3 scripts/foundation_run.py --engine podman discovery round028 --action verify --archive PATH`. It uses the candidate verifier and an isolated temporary destination. It must work with the original workspace unmounted. Read-only actions return success when their requested inspection completes and report campaign status in the result. Execution returns success only for a mechanically completed and verified requested operation, including a properly published inconclusive scientific outcome. Use the foundation failure convention with a nonzero result and explicit reason for blocked or failed work. A second live owner returns promptly with status and owner evidence. Preserve and publish the original failure separately from any reporting failure.

Rehearsal uses separate acceptance families and a disposable journal for fault injection. Sealed scientific outcomes stay inaccessible. Reuse an already measured production-scale import or report cut when its entire compatibility and measurement basis match. Carry forward software validation receipts that the new campaign can authenticate. Run the prospective campaign's full freeze once, persisting validated choices and its staged publication. Exercise interruption on disposable inputs or at a genuine resumable boundary of that same freeze. A successful exact-registration freeze is an input to campaign acceptance and research. The launcher must never schedule it again solely to demonstrate that rehearsal completed.

The launcher materializes tracked files for the full commit via Git into a revision-keyed source cache. Verify the cache against Git before executing it. The build context, package snapshot, CLI code, native workers, locks, versioned contracts and host-only additions all have recorded identities. The candidate host adapter takes distinct source and state roots. Every build and qualified import uses the former. Every run, GPU lock and engine cleanup uses the latter, including `run-state/gpu.lock` at the same physical file used by the donor. Explicitly thread these through legacy module-global root users. No symlinked state roots or mutable hard links. Containers mount only the declared input projections read-only and their own output writable, with no runtime socket. Use new image tags plus immutable IDs and verify them immediately before invocation. Historical source, image tags, trial decisions, recovery scripts and indexes retain their identities.

## Budgets, capacity and timeouts

The initial target is about one eight-hour **GPU shift after qualification**, with at least half targeted for evaluation and replication. Forecast both GPU-active time and exclusive device-lease time across every required arm, look, panel and seed. If occupancy is unavailable, plan conservatively with exclusive lease or measured full-stage elapsed and label that upper estimate. Include preparation, historical costs, retries and reporting in the total resource ledger with their actual scope. Use measured cold and warm service times and uncertainty. If the full registered branch cannot fit, stop before the new expensive dispatch and report the attainable scope and deficit. Adjust scope only under a prospective registration. The shift and heartbeat intervals do not kill workers.

For each physical filesystem, estimate the peak of simultaneous persistent and scratch allocations over the actual stage schedule, including image/build storage where shared, candidate shards, model and optimizer checkpoints, calibration/projection and both staged and published report forms. Subtract already materialized compatible allocations **once**. Account for cleanup staging, streams, bytes, inodes and the actual shared backing device. Report allocation basis (allocated blocks versus file length), compression, and assumptions about shared extents. Compare incremental demand and justified margin with current available capacity at preflight and again before expensive dispatch. Publish a numerical shortfall and a resumable boundary. Automatic deletion is outside the operator contract.

For every new or tightened hard guard require a machine-readable record of owner, protected harm, scope/units, inherited or new value, source of measurement, largest/slowest valid case, reserve/margin and exhaustion action. Prefer observation when the invariant is already covered. If a hard guard is critical before production measurements exist, use a documented generous provisional value based on actual storage, device capacity or the closest larger valid production workload. Name the workstation case that will validate or revise it. Do not promote a toy fixture, sample cadence, expected runtime or project target into an operational timeout.
