# Feature Specification: Trustworthy Experiment Foundation

**Feature Branch**: `007-experiment-foundation`

**Created**: 2026-09-16

**Status**: Specification and implementation design complete; implementation pending.

**Input**: Complete the shared foundation needed to compare macro-WAT and native LODA fairly, using programs learned from generic bootstrap data, twenty observed terms, and the available Ryzen workstation. Minimize experiments and preserve evidence of what was actually measured.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Trust an accepted program (Priority: P1)

As a researcher, I need every accepted program to have the declared arithmetic and execution behavior, so runtime defects, invalid transformations, and resource failures cannot be mistaken for discoveries or model progress.

**Why this priority**: Incorrect accepted programs corrupt training examples and conclusions.

**Independent Test**: Submit a fixed conformance corpus, including known counterexamples and boundary values, without a model. Compare with an independent exact evaluator and confirm that failures cannot enter the accepted archive.

**Acceptance Scenarios**:

1. **Given** `1 × -1`, a constant of `2^64`, signed bounds and cross-limb carries, **when** they execute singly and in batches, **then** each returns the exact declared result or the same classified failure.
2. **Given** a constant assignment producing 16 where the fitting term is 4, **when** the final candidate is checked, **then** it is rejected regardless of the solver's success flag.
3. **Given** malformed source, an unsupported operation, overflow, nontermination, and a crashed worker, **when** evaluated, **then** outcomes remain distinguishable and the caller regains control within its deadline.
4. **Given** a finite match and a relation incorrectly marked proven by the legacy prover, **when** results are archived, **then** neither acquires a theorem or novelty claim.

### User Story 2 - Measure synthesis from twenty terms (Priority: P1)

As a researcher, I need scores tied to programs generated by the named checkpoint using only the permitted prefix, so I can compare learning progress without hidden-answer leakage or reference-program substitution.

**Why this priority**: A comparison is useful only if its scores measure model synthesis on a fixed population.

**Independent Test**: Use an instrumented deterministic model fixture and a small indexed cohort. Perturb hidden values and confirm that generation and selection are unchanged while verification changes appropriately.

**Acceptance Scenarios**:

1. **Given** 100 consecutive exact terms, **when** a checkpoint is evaluated, **then** it sees precisely the first 20 and the evaluator alone checks the remaining 80.
2. **Given** duplicates, matching prefixes with different continuations, or detectable shifted copies, **when** the cohort is frozen, **then** related records stay in one partition and one representative per group contributes to the primary denominator.
3. **Given** several prefix-matching candidates, **when** hidden values are opened, **then** the candidate set and selected top-one candidate have already been frozen; any-of-budget and selected top-one success are separate.
4. **Given** a missing/incompatible checkpoint or incomplete truth, **when** evaluation is requested, **then** no qualifying model score or canonical-reference substitution is emitted.
5. **Given** final-test data, **when** evaluation is requested before checkpoint and stopping decisions are locked, **then** the request is rejected without returning final scores.

### User Story 3 - Preserve the strict learning track (Priority: P1)

As a researcher, I need an auditable route from mechanically sampled generic programs to verified training examples, so the primary experiment investigates learning without supplied sequence solutions.

**Why this priority**: Imported solutions change the scientific question even if accuracy improves.

**Independent Test**: Attempt to admit generated, imported, teacher-produced, corrupted, truncated and legacy records into a small pool; verify provenance, exact execution, serialization and holdout exclusions before the learner can read them.

**Acceptance Scenarios**:

1. **Given** a generic program with a seed and generator version, **when** independent outputs and a lossless token round trip agree, **then** it may enter the strict pool with linked evidence.
2. **Given** an imported solution, named-family teacher, metadata scaffold, legacy replay or unaudited weights, **when** strict training starts, **then** it rejects the artifact with an explicit reason.
3. **Given** an unknown token, truncated constant, missing conditioning prefix or unverifiable continuation, **when** admission runs, **then** the record is excluded before an update.
4. **Given** a generated prefix colliding exactly with a reserved evaluation prefix, **when** admission runs, **then** it is excluded by an evaluator-owned membership check revealing no hidden values.

### User Story 4 - Run and resume on the workstation (Priority: P1)

As the operator, I need bounded, reproducible runs on the Ryzen machine, with isolated dependencies and truthful resource accounting, so multi-day work resumes without silently changing the experiment.

**Why this priority**: Restart errors, configuration drift and device fallbacks can waste the comparison budget.

**Independent Test**: Interrupt/resume a deterministic CPU fixture and compare its next examples, update and budget counters with an uninterrupted fixture. Separately run a real-model GPU update probe and inject worker/resource failures.

**Acceptance Scenarios**:

1. **Given** a complete update-boundary checkpoint, **when** training resumes in the same deterministic CPU environment, **then** next examples, next update, counters and cumulative budget agree with uninterrupted execution.
2. **Given** weights alone or incompatible profiles, **when** resume is requested, **then** it fails; any separately permitted restart receives a new identity.
3. **Given** unavailable GPU support, **when** readiness is checked, **then** it reports `hardware_not_ready` and cannot pass by using CPU.
4. **Given** declared quotas/deadlines, **when** a worker hangs or a limit is reached, **then** failure is contained, recorded, and followed by replacement or a recoverable stop.
5. **Given** an unknown setting or an option for a disabled subsystem, **when** configuration is loaded, **then** validation fails before training.

### Edge Cases

- Signed bounds, zero, negative multiplication, carries, division by zero and signed minimum divided by -1; native-width wrap versus logical wide overflow.
- Missing, duplicate, nonconsecutive or contradictory indices; negative OEIS offsets; fewer than 100 terms; out-of-range values anywhere in the horizon.
- Identical prefixes with different continuations: ambiguous observations, not permission to discard inconvenient targets.
- A prefix match timing out later, incomplete output, failure on the last term, or aggregate budget exhausted before a per-call limit.
- Crash before result acknowledgment, duplicate result delivery, interrupted checkpoint replacement and disk exhaustion during serialization.
- Reusing final-test data after tuning, asynchronous generation beyond a saved cursor, and different worker completion orders.
- CPU diagnostics without a GPU; unavailable native runtime; GPU nondeterminism; measured zero versus disabled/unavailable metrics.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every candidate, admitted example, checkpoint and evaluation MUST reference immutable, versioned language, numerical, entry-point and resource profiles; incompatible identities MUST fail before execution or resume.
- **FR-002**: The initial WAT control MUST check each logical signed-256 result against `-2^255 <= x < 2^255`. Native-width operations MUST retain declared bit-vector semantics; internal carry arithmetic MUST NOT itself be mistaken for logical overflow.
- **FR-003**: Acceptance and admission MUST use independent exact conformance checks whose expected arithmetic does not call production wide helpers or lowering. Mandatory regressions and deterministic differential samples MUST have zero unexplained disagreements.
- **FR-004**: Enabled entry points MUST share final-source validation, execution and comparison rules. Constant assignments and transformations MUST be rechecked after modification; unvalidated optional paths MUST be disabled for qualifying runs.
- **FR-005**: Evidence MUST distinguish invalid syntax/types, unsupported features, numeric limits, execution limits, runtime failures, wrong values, incomplete outputs, prefix matches and full-horizon matches. Operational errors MUST NOT be relabeled mathematical failure or success.
- **FR-006**: Execution MUST declare fresh-state behavior, finite per-call and aggregate budgets, bounded memory and an external deadline. Worker failure MUST NOT crash the controller or prevent outcome recording and reclamation.
- **FR-007**: Benchmark records MUST preserve exact indexed terms, source hash, completeness, range eligibility and grouping provenance. The initial profile MUST rebase the first supplied term to model index zero, retaining the original OEIS index only as evaluator provenance.
- **FR-008**: The initial benchmark profile MUST require 100 consecutive terms, expose exactly 20 to generation/fitting/selection, and reserve 80 for evaluator-only verification. Hidden evaluation values MUST be inaccessible to training, generation and selection.
- **FR-009**: Development/final manifests and groups MUST be frozen before the run. Final scores MUST remain unavailable until checkpoint, selector and stopping decision are locked. Grouping limitations and exclusions MUST be reported.
- **FR-010**: Primary scores MUST count unique representative groups with full-horizon matches at a declared attempt/time budget. Selected top-one MUST be separate from any-of-budget success; duplicate IDs or repeated candidates MUST NOT inflate either score.
- **FR-011**: Every model score MUST link the actual loaded checkpoint, visible prompt, attempts, selected candidate, executable source, verification evidence and effective configuration. Reference-kernel checks MUST remain separately labeled diagnostics.
- **FR-012**: The strict track MUST start from random weights and accept only mechanically generated generic-program demonstrations. It MUST reject imported solutions, named-family teachers, metadata scaffolds, unaudited replay and pretrained/legacy weights. Language primitives and sampling priors MUST be disclosed.
- **FR-013**: Admission MUST require exact verified outputs, lossless token round trips, the complete conditioning prefix and provenance. Unknown tokens, truncation, fabricated extrapolations and exact reserved-prefix collisions MUST be rejected with auditable reasons.
- **FR-014**: A resumable checkpoint MUST restore every active learning, randomness, data-order and budget state at a completed update boundary. Partial checkpoints MUST NOT be selected; weights-only restart MUST NOT be represented as continuation of a strict run.
- **FR-015**: Configuration MUST reject unknown keys and inactive options and persist effective settings before work. Reports MUST distinguish measured values, disabled features and unavailable measurements.
- **FR-016**: The ledger MUST record actual elapsed budget, device use, generator attempts/yield, examples/updates, candidate outcomes, token counts and resources. Proxies MUST be labeled and MUST NOT populate fields claiming direct measurement.
- **FR-017**: On NixOS, dependencies beyond a simple Python virtual environment MUST run in Docker. Readiness MUST inspect existing host GPU support and verify real parameter updates on the requested accelerator without silently installing host components or substituting CPU.
- **FR-018**: Runs MUST enforce finite execution, worker, queue, cache, checkpoint, log and disk limits and demonstrate recoverable handling of injected failures before a long experiment.
- **FR-019**: Finite matches MUST NOT be described as proofs or novel relations. The legacy proof path MUST be unable to promote 007 evidence to `PROVEN`; imported proof labels MUST not cross this boundary.
- **FR-020**: This feature MUST include an explicit constitution amendment proposal and migration/conflict map for earlier specs. Implementation MUST enforce the adopted experimental profile and preserve historical labels without retroactively qualifying old runs.

### Key Entities

- **Experiment contract**: profiles, permitted data, evaluation protocol, effective configuration and runtime identities.
- **Sequence record and split group**: exact indexed truth, prefix, eligibility, related records and one scoring representative.
- **Program record**: source, tokens, origin, seed, profile and independent validation evidence.
- **Candidate evidence**: attempt, final source, resources, classified outcome and finite verification scope.
- **Checkpoint and run ledger**: continuation state, identities, budgets, events and recovery lineage.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All mandatory arithmetic/solver/transformation counterexamples are rejected or return independently expected results; no unexplained differential disagreement is admitted through any enabled single/batch path.
- **SC-002**: Every primary success has 100 exact matches and complete checkpoint/candidate evidence; missing truth or checkpoint yields zero qualifying scores. Hidden-value perturbations leave all pre-verification generation/selection artifacts unchanged.
- **SC-003**: Every admitted example has permitted provenance and exact verification; every prohibited example in the negative admission corpus is rejected before the first update.
- **SC-004**: Deterministic CPU interruption/resumption yields identical next-example identities, next-update state and budget counters. Incompatible/partial checkpoints are rejected; GPU limits are reported separately.
- **SC-005**: Workstation acceptance performs at least three finite, observable model updates on the requested GPU within ten minutes after image availability; all injected worker/quota failures are contained without installing new host toolchains.
- **SC-006**: No 007 result receives theorem or novelty status from finite matching or the legacy symbolic prover.

## Assumptions

- User-confirmed: generic bootstrap from scratch; native LODA first if tested; a minimal initial paired comparison; Ryzen AI Max+ 395 / 128 GB / 2 TB; NixOS with Python and Docker; roughly 1–3 days per arm; **20 visible terms**.
- Explicit planning defaults: 100 total terms (20+80), rebased indices, checked logical signed-256 arithmetic and supervised-only initial learning. Change these versioned choices before freezing a run, never mid-run. The earlier 120-term profile remains historical.
- Meaningful regression, differential, leakage, provenance, resume and containment tests are explicitly required. No model accuracy target is imposed on this infrastructure feature.
- 007 delivers a WAT foundation and a runtime-neutral interface. Native LODA, comparison training, cached decoding, primitive ablations, a transpiler, mixed precision, capacity expansion and full proof repair are deferred.
- This spec does not predict full-OEIS coverage or the fraction of algorithms needing wider intermediates. Prefix range coverage cannot establish those quantities.
