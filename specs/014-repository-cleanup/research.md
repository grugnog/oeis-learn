# Phase 0 research — What the cleanup can safely target

The code baseline is PR #72 at `a2618bbd1ff908a1d720f47268edf4234852c5d8`. Its full tree contains 2,037 tracked files. The first spec 014 commit, `7cfe3356`, adds two documents to that baseline. The observations below come from a full checkout, disposable copies, Git objects and bounded tests. [Reproduction guide](quickstart.md)

## Decisions

| Decision | Rationale | Alternative considered |
| --- | --- | --- |
| Combine syntax and import analysis, exact name/path/hash searches, manual caller tracing and small executions. | Roots include operators, installed entry points, file loaders, build manifests, saved proof versions and public verifiers. Each method sees a different subset. | Using zero imports, one run’s coverage or a dead-code score as permission to delete misses demonstrated consumers. |
| Review outputs, their producers, their default inputs and individual source symbols separately. | The two HPO reports have different dependencies from the script that wrote them. The script itself participates in calibration identity. | Removing a historic directory or experiment wholesale can retire a live default or invalidate a qualification. |
| Compare each group with its parent and transplant each source-changing delta alone onto the passing qualified donor control. | The reporter revision already fails on the first rejected path. Two identical reporter errors can conceal a second incompatibility. | Rewriting receipts or extending an equivalence allowlist would change which evidence an operator can trust. |

## What the tools established

Python 3.12.14 parsed all 1,175 tracked Python files with `ast` (558 under `src`, 487 under `tests`, 75 under `specs`, 48 under `scripts`, six under `tools`, and `setup.py`). There were 18 call sites of the form `*.run_path(...)` and one `*.import_module(...)`. The worker launch embeds `run_module` inside a command string, outside that count. Git text searches covered all tracked paths at the pinned revision, including dot directories. The tests and tools were run outside the live campaign.

Grimp 3.20 found 558 package modules and 3,291 internal import edges. Fifty-seven modules had zero incoming in-package imports. One was `progressive_role`, which has 28 outgoing imports. `progressive_roles._invoke_reserved` constructs the installed worker command with a literal module name, and `progressive_role._execute` selects from 15 operations in `REGISTRY`. An automatic purge of modules with zero importers would disable the campaign. [Host invocation](../../src/oeis_learn/pipeline_validation/progressive_roles.py) · [Worker dispatch](../../src/oeis_learn/pipeline_validation/progressive_role.py)

Vulture 2.16 reported 15 names at 100% confidence under `src/oeis_learn` and `scripts`. Three are `request_stamp`, `batch_stamp` and `qualification_stamp` on `_inventory`. Its caller supplies each file’s inode, size and timestamps. The `lru_cache` decorator uses the arguments to invalidate cached calibration evidence. Removing them would change behavior. The repository’s own `inventory_synthesis_retirement.py --check` passed with zero violations of its specific legacy fitting rules. [Calibration cache](../../src/oeis_learn/pipeline_validation/progressive_calibration_reuse.py) · [Retirement audit](../../scripts/inventory_synthesis_retirement.py)

## Source identity and packaging controls

The source map contains 1,332 keys at `a2618bbd`, including installed-path copies of governance and contract files. Its canonical digest is `sha256:e1c6bfb7838cc0999d2477978bdfa890fb4f504b18b47211771b79bdde37d073`. It covers scripts, tests, native sources, locks and selected contracts. The source digest, Git revision, wheel resources, image ID, native binary identity and saved campaign bindings have different inputs.
